# Sabah-MoE-Accelerator

**A streaming MoE inference runtime for RAM-constrained machines.**

Sabah runs models far larger than the machine's VRAM + RAM combined. It does that
**without a RAM tier, without the page cache and without the page file**: the
expert path goes `disk -> pinned staging -> VRAM` with `FILE_FLAG_NO_BUFFERING`,
so **host RAM stays flat** for the whole run.

That is the point of the project. An 83.6 GB MoE model either fails to load on a
16 GB-VRAM / 15 GB-RAM machine, or it "runs" only by letting the OS page weights
through RAM â€” which requires a large page file and makes latency unpredictable.
Sabah is built for the machine that has **the VRAM but not the RAM**.

Measured end to end on the reference rig:

| | |
|---|---|
| model | `Qwen3.8-Flash-Next` IQ3_S, **83.6 GB** (2 shards, 48 blocks x 512 experts, top-10) |
| time to first token | **11.2 s** (the 53-token prompt is easy; the expert tier starts empty and fills 12.68 GB at 1.11 GB/s) |
| decode, steady state | **~67 ms/token = ~15 tok/s**, effectively disk-free (4.5 reads, 3.0 MB/token) |
| decode, first 128 tokens | 79-204 ms/token: the tier is still discovering its working set |
| 256-token answer end to end | 11.2 s + 24.6 s = **7.1 tok/s including the fill**, 10.4 over the decodes |
| **host RAM** | **flat at 4.78 GiB**, never grows, `mapped_fallbacks=0` |
| peak VRAM | 15.36 GB of 16.31 GB |
| correctness | byte-exact against the GGUF ranges (`verify_ok=64191 verify_fail=0`) |

The shape matters here, so it is worth stating plainly: this runtime is fast once
warm and slow to get warm, because the tier (9.8 GB) is smaller than the working
set of a fresh prompt (12.68 GB of cold fill) and has to learn it. One long answer
runs at 15 tok/s; many short ones pay ~11 s each before the first token. The full
breakdown, per regime, is in [`docs/DECODE_BUDGET.md`](docs/DECODE_BUDGET.md).

Numbers describe the **shipped streaming path** (`sabah/runtime/cuda/sabah_rt.cu`
+ the llama.cpp bridge). The separate Python block-level harness in
`sabah/runtime/*.py` is research scaffolding and is described
[at the end](#python-block-harness-separate-from-the-shipped-path).

---

## Design rules

1. **RAM is not a tier.** Nothing about expert delivery may depend on host memory
   growing. Host RAM is allowed to hold only fixed-size pinned staging buffers
   and loader bookkeeping.
2. **Routing semantics are never changed.** Sabah decides *when* an expert's bytes
   reach the GPU and *where* they are kept. Which experts run, and the input rows
   they are applied to, is exactly what llama.cpp computed. The bridge exists only
   to intercept execution, not to alter it.
3. **Every optimisation must be provable.** Either byte-exact verification against
   the GGUF ranges, or a preserved invariant (for example: a prefetcher is only
   allowed to move bytes in time, so the tier's `hits`/`misses`/`evictions` must
   come out identical).

Rule 3 is why every number in this document comes with the check that proves it.

## How it works

### The tier: VRAM is hot, the disk is cold

There is no intermediate RAM tier. The bank of expert weights is a 50.29 GB pool
of 24576 objects (512 experts x 48 blocks) and it never fits; a VRAM slab
(`SABAH_LLAMA_HOT_BYTES`, 9.8 GB on this rig) holds whatever is currently hot and
everything else is read on demand from the GGUF.

A decode token asks for 480 experts x 3 tensors = 1440 tensor reads (~0.97 GB of
expert bytes). With the 9.8 GB slab, **81.8%** of those hit and **262 reads
(174.7 MB) go to the disk**.

### Direct I/O with pinned staging

Misses are issued as aligned unbuffered reads:

- `FILE_FLAG_NO_BUFFERING | FILE_FLAG_OVERLAPPED`, 4096-byte alignment, so the
  read lands in pinned host memory instead of the OS page cache. The page cache is
  deliberately bypassed â€” it is what would make host RAM grow.
- a double-buffered pinned staging pool (~43 MB) with a wave-boundary event gate;
  `SABAH_LLAMA_IO_DEPTH` (default 8) reads in flight per wave.
- `SABAH_LLAMA_DIRECT_IO=0` switches back to the mapping, for A/B comparison only.

### The llama.cpp bridge

Sabah is not a fork and not a standalone loader; it hooks one operator. Patch
`0001` makes the scheduler keep the original host GGUF expert tensor in the graph
for `MUL_MAT_ID` and hands that op to `sabah_rt_mul_mat_id_v2` together with the
graph's own ids, input and output tensors. Nothing else about llama.cpp changes
and the integration is **opt-in via `SABAH_LLAMA=1`**. See
[`patches/llama.cpp/README.md`](patches/llama.cpp/README.md).

Two placement details are required and easy to get wrong:

- `GGML_OP_OFFLOAD_MIN_BATCH=1`. With `--cpu-moe`, llama.cpp only sends an expert
  op to CUDA when its batch is at least 32 tokens (the default), so every
  single-token decode would silently run on the CPU and never reach Sabah.
- `-ot "\.per_layer_token_embd\.weight=CPU"`. `-ngl 99` alone pushes the 28.8 GB
  per-layer token embedding into VRAM. It is dense and read sequentially, so the
  CPU with the file mapping is the right home for it.

### What was optimised, and what it bought

Everything here came from measuring the token, not from guessing. Baseline to
current is **4.37 -> 4.84 tok/s (+11%)**, with no change to the outputs.

| change | cost before | after | tok/s |
|---|---|---|---|
| baseline (per-call stream drain, linear erase) | `ids` 87 ms | | 4.37 |
| reuse the router ids across a layer's 3 expert tensors | 87 ms | ~23 ms | 4.75 |
| single-scan residency memo per call | | | 4.79 |
| swap-and-pop eviction instead of `vector::erase` | `slot` 30 ms | ~11.5 ms | **4.84** |

**Router id reuse** is the interesting one. The three expert tensors of a MoE
layer (`gate`, `up`, `down`) read the *same* `selected_experts` tensor, so two of
the three `cudaStreamSynchronize` per layer are redundant. The bridge passes
`dst->src[2]` â€” the ids *tensor address* â€” so the runtime can recognise "same
tensor as the previous call" and skip both the download and the drain. Groups are
capped at `SB_ID_GROUP_MAX=4` calls, and that cap doubles as the width of the
eviction-protection window, which is what makes it safe to free a slot while a
kernel enqueued before the last drain may still be reading it.

Removing those drains exposed a latent race worth recording: the pointer table is
**one** shared device buffer that every call rewrites, and the upload used to run
on the copy stream. The drains had been supplying that ordering implicitly. The
upload now runs on the compute stream. (A run with the racy order reported
9.90 tok/s and 23% fewer bytes; those counters are not reproducible and that run
is not trusted.)

### Prefetch is off by default, on purpose

A staging-readahead prefetcher exists (`SABAH_LLAMA_PREFETCH=1`) and is correct:
it reserves no tier space and leaves `hits`/`misses`/`evictions` identical to a
prefetch-free run. It is off because it does not pay â€” adding reads in flight
raised the drive's effective rate (1.3 -> 1.6 GB/s) but not the wall clock, and
40% of the readahead was superseded before anyone asked for it. It becomes worth
revisiting when the disk term drops below the bookkeeping term.

## The measured decode budget

A generation has three regimes and they must not be averaged:

| regime | cost | what limits it |
|---|---|---|
| **time to first token** (53-token prompt) | **11.2 s** | the tier's cold fill: 12.68 GB at 1.11 GB/s |
| **warm-up** (first ~128 decodes) | 70.6 MB/token of disk, 79-204 ms/token | the tier still discovering its working set |
| **steady state** (~15 tok/s, ~67 ms/token) | 3.0 MB/token, 4.5 reads/token | the no-disk floor - the disk is off the critical path |

End to end a 256-token answer is 11.2 s + 24.6 s = **7.1 tok/s including the
fill**, 10.4 tok/s over the decodes alone, 15 tok/s once warm. Full method, phase
attribution and the per-regime lever table: [`docs/DECODE_BUDGET.md`](docs/DECODE_BUDGET.md).

The warm-up token, phase by phase (differencing `-n 32` minus `-n 8`, i.e. decode
steps 9..32 â€” this is the number the README used to quote as *the* rate):

| phase | per token | notes |
|---|---|---|
| `fetch` â€” disk reads + H2D | **121.8 ms** | 164.5 MB/token over 247.4 misses, 82.8% marginal hit |
| `ids` â€” router download + drain | **29.3 ms** | 3 calls per layer |
| `slot` â€” residency bookkeeping | **9.3 ms** | 239 evictions/token, ~39 us each |
| `ptr` + `prime` | **2.8 ms** | |
| outside the bridge (graph, launch, host ops) | **27.7 ms** | residual: phases sum to 163.2 of 190.9 |
| **warm-up decode wall** | **190.9 ms** | median 205.7 ms |

The steady state is the floor and nothing else: measured independently by
replaying a token stream against a warm tier (which reads 0 bytes), **67.3
ms/token**. Two different measurements, same number.

### The disk is the wall for the fill and the warm-up, and it is saturated there

| | |
|---|---|
| drive | MSI M371 1TB NVMe (Gen3 class) |
| drive ceiling, fresh offsets, 676 KB random | **1.05-1.45 GB/s** (repeat-offset probes overstate it ~1.5x) |
| Sabah achieves in the demand path | **1.11-1.35 GB/s** |
| Sabah achieves in the steady state | ~0: 3 MB/token |

So the demand path is **at** the drive's rate, not below it â€” that is lever 2's
conclusion, and it is why raising IO depth or prefetching changes nothing: there
is no unused bandwidth to recover. The dependency chain is also genuinely one
layer deep (layer *L*+1's router needs layer *L*'s expert output), so the drive is
idle during the GPU work and vice versa; a faster drive helps by exactly
`bytes / rate`, which is why the 12.68 GB fill is the most valuable thing on this
list to attack.

## What this project does not claim

- **It reaches 15 tok/s only once warm.** The remaining gap is the fill, which is
  paid once per fresh working set: 12.68 GB at 1.11 GB/s. On a 6 GB/s drive the
  same fill is ~2.1 s and a 256-token answer goes from 7.1 to ~10.5 tok/s end to
  end. The steady state cannot be improved by any storage change at all - it is
  already the floor - and the floor is the model's own per-layer work at batch 1.
- **It is not faster than a machine with enough RAM.** With host RAM allowed to be
  a tier, the warm-up's ~110 reads/token could be served at 0.047 ms instead of
  0.45 ms per expert (measured, [`docs/SECOND_TIER.md`](docs/SECOND_TIER.md)),
  worth ~1.5x on the warm-up and nothing on the steady state. Sabah trades that
  away for a hard guarantee about RAM â€” a deliberate budget decision, not a
  performance claim.
- **Virtual memory does not help.** Windows "virtual memory" is the page file on
  the same NVMe, reached through the page-fault path instead of a 676 KB
  unbuffered read at QD 8 â€” the same bandwidth, a worse access path, no
  controllable queue depth. It adds capacity, and the steady state does not need
  capacity.
- **The GTX 1080 is not used, and measurement says it should not be.** The old
  +18% ceiling assumed the path was cheap. It is not: a park plus a hit through
  the 1080 costs 0.454 ms per expert against the disk's 0.45 ms, with no P2P on
  consumer parts and a gen3 x4 link on the 1080. Break-even at a 100% hit rate and
  worse from there ([`docs/SECOND_TIER.md`](docs/SECOND_TIER.md)).

## Build

**Windows, one click.** `install.bat` automates everything below: it finds Python
and MSVC, reads the GPUs' compute capability, creates `.venv`, installs the
package, builds the runtime DLL for the right architecture and runs
`sabah doctor`. Add `llama` to also fetch the pinned llama.cpp base, apply both
patches and build `llama-sabah-diag`:

```bat
install.bat            :: package + runtime DLL, architecture auto-detected
install.bat llama      :: also the bridge and the measurement driver
install.bat sm_89      :: force an architecture
```

It writes only inside the repository (`.venv\`, `sabah_rt.dll`,
`third_party\llama.cpp`), never to the registry, and it never opens a model. The
steps it automates, by hand:

Requirements: CUDA 12.8, MSVC 14.44 (VS 2022 Professional), CMake.

**1. The runtime DLL** (CUDA kernels, IQ quant types, slab allocator, direct I/O):

```powershell
cd sabah\runtime\cuda
.\build_dll.bat sm_120
```

**2. llama.cpp plus the bridge** â€” reproducible from the pinned upstream base:

```powershell
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git checkout 96ffdc41ceb055e1c2d3d96667ae6d9f0ccb710b
git apply <repo>\patches\llama.cpp\0001-sabah-native-mul-mat-id.patch      # required
git apply <repo>\patches\llama.cpp\0002-sabah-diag-capture-tool.patch       # optional, diagnostics
cmake -S . -B build -G Ninja -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release -DGGML_NATIVE=OFF -DCMAKE_CUDA_ARCHITECTURES="61;120"
cmake --build build -j 8
```

## Run

The integration is inert unless `SABAH_LLAMA=1`. Same model, same flags as an
ordinary `--cpu-moe` run, plus the two placement requirements and the bridge:

```powershell
$env:SABAH_LLAMA        = "1"
$env:SABAH_RT_LIB       = "<repo>\sabah\runtime\cuda\sabah_rt.dll"
$env:SABAH_LLAMA_HOT_BYTES = "9.8e9"          # VRAM expert slab (default 2 GiB)
$env:GGML_OP_OFFLOAD_MIN_BATCH = "1"          # required, see above
$env:SABAH_LLAMA_TRACE  = "1"                 # cache / coverage / phase counters at exit

llama-sabah-diag.exe `
  -m $DRIVE\Strata-data\models\IQ3_S\Qwen3.8-Flash-Next-GSQ-RCO-IQ3_S-00001-of-00002.gguf `
  -dev CUDA0 -ngl 99 --cpu-moe `
  -ot "\.per_layer_token_embd\.weight=CPU" `
  -t 8 -c 512 -n 32 -p "Hello"
```

`llama-sabah-diag` is the measurement driver from patch `0002`. The bridge lives
in `ggml-cuda`, so any llama.cpp binary loads it: `llama-cli` runs this model end
to end as well (verified â€” `EXITCODE=0`, zero mapped fallbacks, generated text,
~27 GB streamed for the same prompt), and so does `llama-server`, which is how a
client reaches this model over HTTP.

`-c 512` above is deliberate, not an oversight. The KV cache and the expert slab
are paid from the same 16.31 GB, and at `-c 32768` a 9.8 GB slab has ~0.4 GB of
headroom left: the run aborts with `SABAH_LLAMA could not execute the
host-backed exact expert operation` / `Sabah over-budget expert: out of memory`
once the tier's documented over-budget allocation has no VRAM to take. Both
sides of that trade, measured, are in
[`docs/CONTEXT_VRAM.md`](docs/CONTEXT_VRAM.md) â€” 32K works with an 8.0 GB slab or
with `-ub 8`.

Two things to know when reproducing:

- **The prompt is 53 tokens, and the first token still costs ~11 s.** The chat
  template around `-p "Hello"` is 53 tokens (the diag writes the ids it used to
  `prompt_tokens.i32`; `prompt.txt` shows the text). The 11 s is the expert
  tier's **cold fill**: 12.68 GB at 1.11 GB/s, all of it before step 1. The
  `tokens=` field in the `SABAH_DIAG` line is a count of expert *rows*
  (`layers x tensors x batch`), not prompt tokens â€” for a 6-decode run it is
  already 8484, which is where an earlier version of this README misread it.
- **Quote decode per regime, not as one number.** `-n 1` is the fill, `-n 128`
  shows the warm-up, `-n 256` reaches the steady state (67 ms/token, disk-free);
  differencing `-n 32` and `-n 8` gives the warm-up marginal token
  (190.9 ms/token), which is *not* the sustained rate. `sabah run` reports all
  three.

### One-command harness

`sabah run` drives the same binary, reads the counters out of it, and reports the
three regimes (fill, warm-up, steady state); `sabah matrix` regenerates the
results matrix as JSON; `sabah gate` runs the correctness switches as pass/fail:

```powershell
python -m sabah.tools.cli run    <model.gguf> --tokens 256
python -m sabah.tools.cli matrix <model.gguf> --out results/matrix.json
python -m sabah.tools.cli gate   <model.gguf>
```

`sabah run` needs `SABAH_DIAG_EXE` (a built `llama-sabah-diag.exe`) and
`SABAH_RT_LIB`; `--diag` and `--rt` override both. The cache counters in every
report come from the runtime's exit snapshot, which is exact â€” so no timed run
sets `SABAH_LLAMA_STATUS_FILE` (the runtime rewrites that file after *every*
expert call, which costs ~0.3 s per token here and turns 14.6 tok/s into 1.9).

### Verification switches

These are the gate, not debugging aids. Run them before believing any number.

| variable | what it proves |
|---|---|
| `SABAH_LLAMA_VERIFY_BYTES=1\|fetch` | byte-compares served expert data (hits, or fetches) against the GGUF range |
| `SABAH_LLAMA_VERIFY_LIMIT` | caps those checks â€” the oracle reads the mapping and inflates host RAM |
| `SABAH_LLAMA_ID_CHECK=1` | forces the ids download even when reused and compares â€” proves the reuse byte for byte |
| `SABAH_LLAMA_TRACE=1` | prints cache, coverage and phase counters |
| `SABAH_LLAMA_IO_WORKERS=1` | reads each wave on the calling thread; `SABAH_IO` then reports `overlap=1.00` instead of ~3.8, with the same wall time |
| `SABAH_LLAMA_LAYER_MERGE=1` | one wave per layer instead of three; halves the wave count and costs ~13 ms/token (default off) |

Measured by `sabah gate` on the reference rig: `verify_ok=2000 verify_fail=0`,
`id_check_ok=768 id_check_fail=0`, exit code 0.

Two things about the run that prints those numbers. First, the `overflow` counter
it also prints (448) is **not** a correctness failure: `overflow` counts
over-budget expert allocations â€” when every eviction candidate is still
referenced by the call in flight, the tier allocates past its budget rather than
dangle a pointer â€” and the byte comparison above is what proves the routed result
stayed exact. The gate reports it and does not fail on it. Second, the exit code
is worth checking: every process that used the direct I/O wave pool used to end
in a fast-fail (`0xC0000409`) *after* the run and its trace had completed,
because the pool's worker threads were never joined. `sabah gate` was the first
thing here to check the exit code, and that is what found it; fixed in
`sabah/runtime/cuda/sabah_rt.cu`.

Third â€” read this before chasing a `differs from its GGUF bytes` failure. The
oracle reads the file through the OS mapping, i.e. the page cache; the runtime
reads it with `FILE_FLAG_NO_BUFFERING`, which the cache cannot answer. Those two
can disagree about the same range, and they did:

- 10 bytes of one 921600-byte expert, at offset 1,367,138,304 of the first shard,
  identical in three consecutive runs, and independent of the I/O path (same 10
  bytes at depth 1, at one worker, and at depth 2 â€” so not a staging race);
- reproduced **outside the runtime and outside llama.cpp** with a plain buffered
  `read()` against an unbuffered `ReadFile` of the same range, while the mismatch
  line named the file, the offset and the byte positions;
- gone on the next run of the same binary, with no change to it.

So this failure means "the served bytes and the cached image of the file
disagree". It does not say which side is stale: a cached page can be older than
the disk, or newer than an unflushed write. What it does say is that the check
fired and that the case needs to be looked at â€” start with the two routes on that
range, not with the streaming path.

## Python block harness (separate from the shipped path)

`sabah/runtime/*.py` is an earlier, independent research harness. It works on a
single block in isolation with synthetic traces, and its tables assume a **pinned
RAM warm tier** â€” the configuration the shipped runtime explicitly forbids. Its
`bench_moe` numbers are per-block and are not comparable to the end-to-end tok/s
above; the two must not be quoted together.

Use it for what it is good at: quant-kernel bit-exactness, planner hit-rate
curves, and prefetch-equivalence tests.

- `python -m pytest tests sabah\tests -q`
- `python sabah\tools\bench_moe.py --model $env:SABAH_MODEL --block 0 --tokens 500 --slots 16,32,64,128,256`

New IQ quant types implemented along the way, validated bit-exact against the
`gguf-py` reference: `IQ2_S`, `IQ3_S`, `IQ3_XXS`, `IQ4_XS`, `IQ4_NL`, `Q2_0`
(plus the existing `Q4_K`, `Q5_K`, `Q5_1`, `Q8_0`).

## What would actually move the needle

Ordered by measured leverage. **The regime decides which lever matters**: the fill
is paid once per fresh working set (11.2 s), the warm-up is the tier learning
(~9 GB), and the steady state is disk-free and only the floor can move it.

| # | lever | effect | cost/risk |
|---|---|---|---|
| 1 | **Gen4/Gen5 NVMe** | the *fill* is 12.68 GB at 1.11 GB/s = 11.2 s of the 35.8 s a 256-token answer takes; at 6 GB/s that is ~2.1 s and the answer goes 7.1 -> ~10.5 tok/s end to end. The steady state does not move (it is disk-free). Re-measure any candidate with fresh offsets (`tools/disk_probe.py`, `tools/io_bench.cu`) - the old 6 GB/s projection used a repeat-read ceiling | money. Still the largest single change for short answers |
| 2 | ~~**Close the exposure gap** (1.31 -> ~2.4 GB/s in the demand path)~~ **measured, no gap to close** | the 2.4 GB/s target was a repeat-read artifact of the old probe: with fresh offsets this drive reads ~1.05-1.45 GB/s and gains only ~15% from one reader to sixteen. The runtime reads at 1.11-1.46 GB/s | n/a. See `docs/DECODE_BUDGET.md` |
| 3 | ~~**Fewer bytes per token** - batch verification / speculative decoding~~ **measured, dead on this rig** | the "982 -> 676 MB/token" figure was residency demand, not miss traffic; measured bytes/position get *worse* with B (164.5 -> 169.6 MB). A 100%-acceptance pass is only 15% faster (161.3 vs 190.9 ms/position), so break-even needs 78-82% acceptance plus rollout, and this rig's `common_ngram_simple_draft` accepts **0.004 drafts/pass** on the model's own greedy stream (99.6% of passes accept nothing; n>=3 never): **2.8-7.7x slower** | high risk, measured net loss for speculation. **What survives: batching real concurrent requests.** The floor is `30.3 + 37/B` ms/position, so B=8 is 34.9 ms = 28.7 tok/s, and a server has independent requests without needing a drafter |
| 4 | **The floor** (the steady state, measured) | 67.3 ms/token with the disk removed entirely = `30.3` per-position work + `37/B` per-call cost, and the per-call cost is the per-layer router drain (ids ~50 ms/token at B=1). # Acceleration layers â€” what changed, and how to test it

Four changes were made to Sabah's own runtime. They are independent, and each
one has a test that fails if it is reverted.

| Piece | What it does | Files |
|-------|--------------|-------|
| **A â€” n-gram prefetch** | The n-gram table (~28.8 GB) is mmap'd read-only, the rows a token will read are hinted into the working set *before* the forward pass, and the previous token's rows are advised away. The table never competes with experts for RAM. | `sabah/runtime/ngram_prefetch.py` (new) |
| **B â€” warm RAM tier** | Leftover usable RAM is pinned as a per-block expert warm tier. A block's experts are then refilled from pinned RAM instead of the SSD. | `sabah/runtime/expert_bank.py` (`load_warm`), `sabah/planner/planner.py` (`warm_bytes`, `warm_blocks`) |
| **C â€” fixed path resident** | The fixed path is charged to VRAM *before* experts, is explicitly marked resident, and the remainder becomes the expert hot tier. A runtime helper pins the fixed tensors. | `sabah/planner/planner.py`, `sabah/runtime/residency.py` (new) |
| **D â€” MTP expert prefetch** | Speculative cross-token expert prefetch. Advice only: it can never change which experts run. | `sabah/runtime/mtp_prefetch.py` (new), `sabah/runtime/hot_tier.py` (`prefetch`, `mark_submitted`) |

## Two correctness fixes to earlier work

These are the reason the DLL must be rebuilt. Both were latent bugs, not
optimizations:

1. **A slot could be overwritten while a submitted kernel still read it.** After
   the earlier "remove the stream sync" change, an evicted slot was reused for
   the next expert's H2D before the kernel that read the old occupant had
   necessarily finished, which can silently corrupt a token. Fixed with a new
   `sabah_copy_wait_event` (copy stream waits on a compute-stream event) plus a
   per-block `mark_submitted` event. The llama.cpp bridge path keeps its
   conservative `cudaStreamSynchronize`, because that entry point does not
   launch the kernel itself and so has no point at which to record "the reader
   is done".
2. **The router-id download was made "async" but the host read it immediately.**
   Reverted to a synchronizing download: the residency decision needs the ids on
   the CPU, and no amount of stream juggling changes that. Overlapping it is the
   job of the MTP prefetcher (predict, don't wait).

The slab allocator was also rewritten as a real best-fit free-list with
coalescing; the earlier version handed the same base pointer to every expert.

## 7. What is deliberately *not* done

* **Eviction-based prefetch.** `HotTier.prefetch` fills only slots the
  `_ensure_locked` reserve keeps free. It never evicts, because evicting a slot
  a submitted kernel may read needs the same "copy waits for its reader"
  ordering that is now in place for misses; extending it to prefetch is a
  contained follow-up, not a silent risk.
* **A real MTP head.** `mtp_prefetch.py` defines the seam
  (`ExternalPredictor`) and ships a `FrequencyPredictor` baseline. The MTP head
  lives in the model/llama.cpp; feeding its candidates into
  `ExternalPredictor` is the integration point.
* **The full expert bank in VRAM.** For the `Qwen3.8-Flash-Next-GSQ-RCO-IQ3_S`
  artifact the expert bank is 50.29 GB (24576 objects, 512 experts Ã— 48 blocks),
  and the fixed path is a further 4.18 GB read every token, so a 24 GB card
  cannot hold either one whole. The path to the target speed is hiding transfer
  latency (prefetch, warm tier, hot tier), not making it all resident.
  Measured per-block kernel cost at full residency is ~0.65 ms/token for block
  0 (~1550 tok/s for that block alone); end-to-end tokens/s is bounded by how
  much of the bank stays resident versus how fast the disk feeds misses
  (measured 1.56-2.01 GB/s sequential on this machine's NVMe).
* **The projection model for the warm tier.** The planner reports the warm tier
  and uses it for the recommendation gate, but does not add a RAMâ†’VRAM
  bandwidth term to the projected tokens/s. That would be inventing a number the
  benchmark should measure instead.


===== docs/ARCHITECTURE.md (pass 1) =====

# Sabah architecture

Sabah preserves the authoritative router decision. If the router selects
expert `E`, the exact stored expert `E` is fetched and executed.

```text
GGUF inspector
    -> exact byte-range profile
    -> mmap/file or RAM backing store
    -> per-device VRAM hot tier
    -> async H2D miss
    -> quantized expert CUDA kernel
```

The backing store is read-only. Expert identity is `(block, expert)` and each
role (`gate`, `up`, `down`) carries its own shard, offset, byte count, and
qtype. The hot tier uses fixed-size per-block slots and LRU replacement.

The current CUDA path is a block executor. It is not yet wired into the full
attention, recurrent/PLE, KV-cache, tokenizer, and sampling graph. The
full-model seam is the local llama.cpp reference engine used by `serve
--allow-reference` while that integration is completed.



===== docs/BENCHMARK_METHOD.md (pass 1) =====

# Benchmark method

There are two deliberately separate measurements:

1. `sabah bench` measures one real MoE block, real expert bytes, a routing
   trace, and hot-tier residency. Its resident-vs-streamed A/B isolates the
   streaming penalty. It is not full-model tokens/s.
2. `sabah benchmark` records a comparable full-model reference invocation and
   its provenance. It prints `Measured speedup unavailable` until a full-model
   Sabah invocation under the same artifact, prompt, context, decoding,
   concurrency, and generation length exists.

Every result should retain the Sabah commit, model hash, runtime command,
hardware, execution plan, and raw timings. `MEASURED`, `PROJECTED`,
`SIMULATED`, and `ORACLE` are not interchangeable labels.

## Any disk number must draw fresh offsets

This drive serves a repeated read about 1.5x faster than a fresh one, so a
probe that draws one offset list and re-reads it for every case reports a
throughput the model can never see. On the reference rig (676 KB reads, the
expert stride, whole file): fresh offsets 1187-1293 MB/s at qd 1-8, the same
list re-read 2318-2320 MB/s at qd 4-8. Every disk number in this repository
before `disk_probe.py` learned to redraw per case - including the 2.4 GB/s that
levers 1 and 2 were projected from - is the second column.

`tools/disk_probe.py` draws fresh offsets per case (`--reuse-offsets` brings the
old behaviour back for comparison); `tools/io_bench.cu` takes a seed and reports
the sum of the individual read calls next to the wall time, so overlap and
throughput can be read separately. `SABAH_IO` prints the same overlap ratio for
the real runtime.

## Decode cost is differenced, never read off a single run

`-n` is `n_predict` and step 0 of the diag's step loop is the *prefill*, so
`-n 1` yields zero decodes. Every per-token number in this repository comes from
running the same configuration at `-n 8` and `-n 32` and dividing the delta by
24: the prompt, the warm-up and the load all cancel, and the tier's own warming
(`~50 tokens`) is spread across both runs instead of being charged to one.

`SABAH_LLAMA_STATUS_FILE` must **not** be set during a timing run: the runtime
rewrites that file after every `MUL_MAT_ID` call (~2 ms each, 144 calls/token).
Counters that only exist in it (hits, misses, evictions, overflow, resident
bytes) come from a separate counters-only pass; the counters are exact, the
timings from that pass are junk.

## A decode number belongs to a regime: fill, warm-up, steady state

Differencing short runs prices the **warm-up** - the marginal token of a
generation that has just started - and that is not the sustained rate. Same rig,
same prompt, same binary, only `-n` differing (53-token templated prompt):

| run | disk reads | disk bytes | what it is |
|---|---|---|---|
| `-n 1` (prefill only) | 20087 | 12.68 GB | the **fill**: 12.68 GB before the first token, 11.3 s at 1.11 GB/s |
| `-n 128` minus `-n 1` | 13932 | 8.75 GB | the **warm-up**: 109.7 reads / 70.6 MB per token |
| `-n 256` minus `-n 128` | 579 | 0.38 GB | the **steady state**: 4.5 reads / 3.0 MB per token |

The fill reads more than the 9.8 GB tier holds because the tier is still evicting
while it fills; that is why it is 12.68 GB, not 9.8 GB. The steady state needs no
disk at all, which is why no storage number can be quoted as "the decode rate".

So quote every rate with its window, or quote all three. `sabah run` performs the
split itself from `step_ms.f64` (step 0 is the fill; `regimes(out_dir,
warm_tokens=128)` is the boundary), and `step_ms.f64` is written in the normal
path too, not only under `SABAH_DIAG_MANIFEST`.

## The verification oracle reads the cache; the runtime does not

`SABAH_LLAMA_VERIFY_BYTES` compares the served expert bytes against the GGUF
through the **memory mapping** (the page cache). The runtime's own reads use
`FILE_FLAG_NO_BUFFERING`, which bypasses the cache. The two are allowed to
disagree about the same range:

| observed | value |
|---|---|
| object | one 921600-byte expert, offset 1,367,138,304 of shard 1 |
| disagreement | 10 bytes, isolated, in a 170-byte window (`first=635221..635389`) |
| runs | the same 10 bytes in three consecutive runs |
| I/O depth 1 / one worker / depth 2 | the same 10 bytes (so not a staging race) |
| outside the runtime | a buffered `read()` vs an unbuffered `ReadFile` of the same range disagree identically |
| next run of the same binary | agrees again, no rebuild |

So a verification failure means "the served bytes and the cached image of the
file disagree"; it does not by itself say which side is stale - a cached page can
be older than the disk (a page that survived a rewrite) or newer than an
unflushed write. When it fires, compare the two routes on that range before
suspecting the streaming path. `SABAH_VERIFY_MISMATCH` prints the byte count, the
number of differing bytes, the first differing positions and the resolved file
and offset, and the host-visible error names them too.

## The no-disk floor: replay one stream against a warm tier

To measure what a decode costs with the disk removed, run several prompts in one
process with `SABAH_DIAG_MANIFEST` (the KV is cleared between items, the expert
tier is not) and give every item the *same* `SABAH_DIAG_FORCE_DIR/<id>/fed.i32`
token stream. Items after the first re-touch exactly the same `(tensor, expert)`
objects, so their disk demand collapses: with a working set far under the tier
they read literally 0 bytes, and their step times are the floor.

Two rules make it trustworthy:

* The working set of one item must fit the tier comfortably (a 4-token prompt and
  8-64 forced tokens; not the real prompt's 53 tokens plus a long stream), or the
  items thrash against each other and the "warm" items are not warm. Confirm with
  the trace: the whole-run `SABAH_DISK` byte count must equal one item's cold
  demand, i.e. it must not grow with the item count.
* In the normal path `step_ms[0]` is the prefill and must be dropped; in the
  batch-probe path (`SABAH_DIAG_BATCH_PROBE=B`) every `step_ms` entry is one
  pass, including the first. Dropping the first entry there silently deletes a
  measurement (it once turned the B=8 case into a column of zeros).

`measure_l4_floor2.ps1` in the working notes is the reference script: 6 items x
8 tokens at B = 1, 2, 4, 8, reporting per-position cost with the cold item
excluded.




===== docs/CLOCK_HYGIENE.md (pass 1) =====

# Clock hygiene

A decode measurement on this machine is only comparable with another one if the
card was at the same clocks. It is not pinned by default, and the driver's
adaptive policy does not simply "stay at boost while a model runs": on this
workstation the card steps **down** to P3 mid-decode when the host leaves gaps
between kernels, then steps back up. That is a closed loop with the workload,
so the same binary can measure 44 ms/token or 89 ms/token.

## What the 1 s trace shows

`tools/clock_trace.py` samples SM clock, memory clock, P-state, power, utilisation,
display state and the throttle bitmask once a second across idle -> decode -> idle.

Decode, **unpinned** (256 tokens, `-c 512`, 6.0e9 slab, TILE3 on):

| t (s) | SM MHz | mem MHz | P | W | state |
|---|---|---|---|---|---|
| 0-15 | 412-472 | 405 | P8 | 8.3 | idle |
| 16-21 | 2617-2857 | 13801 | P1 | 17-32 | ramp |
| 22-29 | 1470 -> 825 | **7001** | **P3** | 20-21 | **downclocked mid-decode** |
| 30-31 | 2392-2422 | 7001 | P3 | 32 | recovering |
| 32-40 | 2400-2527 | 13801 | P1 | 34-38 | partial |
| 41-51 | 2820-2842 | 13801 | P1 | 76-86 | full boost |

The 7 s P3 / 7001 MHz window is the 88.9 ms episode in miniature: kernels
stretch, the host waits, utilisation stays low, and the driver keeps the low
state a little longer. It recovers only when the expert tier warms up and the
GPU duty cycle rises.

The same decode with **`-lgc 2800,3090` only** (minimum pinned, maximum free)
holds SM at 2805-2842 MHz for the whole run (0 of 59 samples low), **but the
memory clock still drops to 7001 MHz for 7 s**. Pinning the SM floor alone is
therefore *not* enough on this card.

With **`-lgc 2800,3090 -lmc 13000,14001`**, SM stays 2805-2842 MHz and memory
stays 13801 MHz for the whole run, idle included.

## Pinning (needs an elevated shell)

```powershell
# pin: SM floor 2800 MHz, memory floor 13000 MHz, ceilings left at stock
nvidia-smi -lgc 2800,3090
nvidia-smi -lmc 13000,14001

# verify
nvidia-smi --query-gpu=clocks.sm,clocks.mem,pstate,power.draw --format=csv,noheader

# restore default clock management (do this after every batch)
nvidia-smi -rgc
nvidia-smi -rmc
```

Notes:

* `-lgc` takes `min,max`. Only the minimum is needed; the maximum is left at the
  stock 3090 MHz so the card can still boost above 2800.
* Pins are not persistent: a reboot or driver restart clears them. They are also
  not applied at idle the same way â€” with the pin active the card idles at
  P1/2805 MHz/~26 W instead of P8/430 MHz/~8.4 W. Unpin when finished.
* Nothing here changes the driver, the power limit (180 W) or the throttle
  reasons. `clocks_throttle_reasons.active` reads `0x400` (reliability) both
  pinned and unpinned; it is not the cause of the downclock.

## How a run is declared valid

`tools/phase0_measure.py` and `sabah bench` start a `sabah.tools.clocks.ClockSampler`
(0.5 s resolution) for every run, and write the whole-run and steady-window
statistics into the measurement JSON:

* `clocks.steady.sm_mhz` â€” min/median/max over the decode window
  (the tail of the run the decodes occupy);
* `clocks.steady.mem_mhz`, `pstate`, `power_w`, `throttle`, `display_active`;
* `clocks.valid` â€” false when the steady SM median is below **2400 MHz**
  (or the memory median is below **10000 MHz**), with `clocks.reason`;
* `machine` â€” power plan, HAGS key, NVIDIA power-management registry values,
  driver version and power limits, display state.

An invalid run exits **4** (driver failures still exit 3). `--allow-low-clock`
keeps the exit code at 0 while still marking the record invalid â€” use it only
when the low clock is the thing being measured.

Machine state at the time of these traces: Windows power plan **Balanced**
(`381b4222-f694-41f0-9685-ff5bb260df2e`), HAGS key **absent (off)**, display
**attached and active**, driver **617.42**, power limit **180 W** (default 180,
max 200), no `PowerMizer*` overrides in the driver registry.

===== docs/CONTEXT_VRAM.md (pass 1) =====

# Context size and the VRAM slab

The expert slab and the KV cache are paid from the same 16.31 GB. Every gigabyte
the context takes is a gigabyte the slab cannot hold, and the slab is what makes
the decode cheap: 9.8 GB holds the working set (steady state, 3.0 MB/token of
disk), 1 GB does not (559 ms/token). So "can this run at N context" is not a
question about the model. It is a question about which side of that trade the
run lands on â€” and one of the answers is a hard abort, not a slow token.

Everything below is measured on the reference rig (RTX 5060 Ti 16 GB `sm_120`,
15.38 GiB RAM, MSI M371 NVMe; the model and flags are the ones in the README's
Run section). Hardware and method caveats are in
[`docs/BENCHMARK_METHOD.md`](BENCHMARK_METHOD.md).

## Summary

| context (`-c`) | slab (`SABAH_LLAMA_HOT_BYTES`) | ubatch | result |
|---|---|---|---|
| 512 | 9.8e9 | default | works â€” the README's headline configuration |
| 8192 | 9.8e9 | default | works |
| 32768 | 9.8e9 | default | **abort** (VRAM exhausted), 3 of 3 runs |
| 32768 | 8.0e9 | default | works â€” the slab pays for the context |
| 32768 | 9.8e9 | `-ub 8` | works â€” the prefill pays for the context |
| 131072 | 6.0e9 | default | works - full speed (17.2 tok/s) |
| 131072 | 9.8e9 | default | works, but 34% slower (11.3 tok/s) at the VRAM ceiling |

The `-ub 8` row is `llama-server` only â€” the diag driver takes no ubatch argument,
and that driver is the one that aborts at `-c 32768` with the 9.8 GB slab. The
512 row is the README's headline run; the rest were run for this note, each with
`sabah run --tokens 32` and, where a ubatch applies, with `llama-server`, at the
same prompt.

The abort is not a hard context limit: the Phase 0 measurement ran `-c 131072`
with the same 9.8 GB slab through the diag driver for 255 decodes and exited 0
(88.4 ms/token, peak 16,000 MiB). It sits at the same ceiling the 32K run
aborted at, so whether a run survives is decided by the timing of the
over-budget allocation against whatever free block is left - which is also why
that configuration is 34% slower there (see "128K context" below).

`-c 32768` with a 9.8 GB slab *loads* and even survives a one-token decode
(peak 15,892 of 16,311 MiB). It dies once the run is long enough for the
over-budget path to need a device allocation that no longer fits. Both the
diagnostic driver and `llama-server` fail this way; where the boundary sits
between 8K and 32K was not located.

## The failure is VRAM exhaustion, not a routing error

`ggml-cuda.cu` hands every host-backed `MUL_MAT_ID` to the bridge, logs the
bridge's error if it refuses (`ggml/src/ggml-cuda/ggml-cuda.cu:269`) and aborts
the process (`:2058-2064`):

```
$DRIVE\...\ ggml\src\ggml-cuda\ggml-cuda.cu:2061: SABAH_LLAMA could not execute the host-backed exact expert operation
0.16.573.058 E SABAH_LLAMA MUL_MAT_ID failed: Sabah over-budget expert: out of memory
```

That second line is the real cause. The tier's documented over-budget behaviour
(`sabah/runtime/cuda/sabah_rt.cu:628`, `sb_mmid_reserve_locked`) is: take space
from the slab, and when the slab is full and nothing can be evicted, count an
`overflow` (`:643`) and allocate the expert outside the budget rather than fail
the call. That follow-up `cudaMalloc` **is** checked (`:644`) â€” and on a 16 GB
card at 32K context there is no room left for it, so the call returns `nullptr`
and the process aborts.

The counters at the moment of the abort, read from `SABAH_LLAMA_STATUS_FILE`,
show a run that routed normally and simply ran out of VRAM â€” 68.7% of lookups
served from the tier, `mapped_fallbacks` never in play (the fields that matter,
of a longer object):

```json
{"calls":506,"tokens":7416,"lookups":73428,"hits":50464,"misses":22964,
 "evictions":8735,"bytes_fetched":15464409600,"resident_bytes":9799513600,
 "overflow":485,"verify_ok":0,"verify_fail":0}
```

`overflow=485` is the tell: the tier was already allocating past its budget
before the allocation that failed. With more headroom the same counter climbs and
the run still exits 0 (982 at `-c 8192`, 1239 at `-c 32768` with an 8.0 GB slab,
both 32 tokens) â€” so `overflow` is not the failure, the *absence of VRAM behind
it* is.

Two notes on reading the exit code. The abort surfaces as `3221226505`
(`0xC0000409`), which is also what the **fixed** exit-time fast-fail used to
produce. They are not the same event: that one happened after the trace had been
written, this one happens mid-decode with the `GGML_ABORT` line above on stderr.
And because the runtime prints its counters from an `atexit` handler
(`sb_report_diag`, `sabah/runtime/cuda/sabah_rt.cu:2839`, registered at `:2916`
and gated on `SABAH_LLAMA_TRACE`), an abort means the `SABAH_DIAG` /
`SABAH_DISK` / `SABAH_SNAPSHOT` lines are **never printed at all** â€” an aborting
run reports no counters unless `SABAH_LLAMA_STATUS_FILE` is set.

## Peak VRAM, measured

`nvidia-smi`, sampled every 0.5 s; total is 16,311 MiB.

| configuration | peak | headroom |
|---|---|---|
| `-c 512`, slab 9.8e9 (README headline) | 15,360 | 951 |
| `-c 32768`, slab 9.8e9, one decode token | 15,892 | **419** |
| `-c 32768`, slab 9.8e9, default ubatch | 15,605 at load, then abort | â€” |
| `-c 32768`, slab 9.8e9, `-ub 8` | 15,223 | 1,088 |
| `-c 8192`, slab 9.8e9 | 14,804 | 1,507 |
| `-c 32768`, slab 8.0e9 | 13,823 | 2,488 |

### 128K context: the context is cheap, the last 300 MiB are not

Measured with `-c 131072 -n 256`, same flags. The KV cache at 131,072 cells is
**384 MiB at f16, 204 MiB at q8_0, 108 MiB at q4_0** (llama.cpp's own
`KV buffer size` line): only 12 of the 48 blocks keep a cache
(`full_attention_interval=4`), it is **K-only** (V is empty), 2 KV heads x 128
elements. The compute buffer is 964-976 MiB. The context itself costs ~1 ms of
decode.

What costs 30 ms is running the slab into the VRAM ceiling. Same prompt, same
131.6 misses/token, same kernel set:

| `-c` | slab | steady median | tok/s | VRAM plateau | free |
|---|---|---|---|---|---|
| 512 | 9.8e9 | 58.34 ms | 17.14 | 15,367 | 916 |
| 8192 | 9.8e9 | 58.39 ms | 17.13 | 15,475 | 808 |
| 32768 | 9.8e9 | 60.04 ms | 16.65 | 15,982 | 301 |
| 131072 | 6.0e9 | **58.23 ms** | **17.17** | 15,377 | 906 |
| 131072 | 7.0e9 | 63.29 ms | 15.80 | 15,991 | 292 |
| 131072 | 8.0e9 | 71.54 ms | 13.98 | 15,994 | 289 |
| 131072 | 9.8e9 | 88.43 ms | 11.31 | 16,000 | 283 |
| 131072 | 9.8e9, `-ub 64` | 79.29 ms | 12.61 | 15,988 | 295 |

An Nsight capture at 128K / 9.8e9 shows GPU busy 92.3 ms/token with
`k_mul_mat_id` at 465 us/call against ~188 us at 512 context: the same kernel on
the same bytes, 2.5x slower within 300 MiB of the ceiling. At a 6.0 GB slab the
run reads 149.5 objects/token instead of 131.6 (14% more bytes) and is still full
speed - the extra reads overlap, the pressure does not.

The counters say why (`tools/gpu_mem_probe.ps1` samples
`\GPU Adapter Memory(*)\Dedicated Usage` / `Shared Usage` and the per-process
`\GPU Process Memory(*)\Dedicated/Shared Usage`). Per-process medians at
`-c 131072`:

| slab | dedicated | shared | steady |
|---|---|---|---|
| 6.0e9 | 14,916 MiB | 304 MiB | 58.2 ms |
| 7.0e9 | 15,479 MiB | 750 MiB | 63.3 ms |
| 8.0e9 | 15,471 MiB | 1,824 MiB | 71.5 ms |
| 9.8e9 | 15,469 MiB | 3,623 MiB | 88.4 ms |

(The same 9.8e9 slab at `-c 512` holds 110 MiB shared and runs at 58.3 ms.)
Dedicated saturates at ~15.47 GB of the adapter's 15.99 GB used; the rest of the
budget is not resident. That excess is WDDM oversubscription into shared system
memory, read over PCIe - so the rule is about the whole footprint, not the slab:
model 3,983 + slab + compute 976 + KV 384 + context must fit in ~15.4 GB.

So 128K is affordable in KV and is paid for in slab: **6.0e9 is the value that
keeps this workload at full speed at `-c 131072`**; 9.8e9 costs 34% because 3.3 GB
of it lives in system RAM. Other processes hold 728-731 MiB of dedicated, so
closing them would move the safe slab to ~6.7e9, not remove the oversubscription.

The 32K KV cache costs less than the header arithmetic suggests. From the GGUF:
48 blocks, 2 KV heads, key/value length 256, f16 â€” 2 KB per token per block, i.e.
96 KB per token summed over all 48 blocks. That is the upper bound (3.22 GB at
32K) *if every block kept a full cache*. The measured peak difference between
`-c 512` and `-c 32768` at the same slab is **~0.5 GB**, because this model does
not grow a cache on every block (`full_attention_interval: 4`,
`attention.compress_ratios` of `0,0,0,4` per group). So the context is not
expensive here; the *margin* is. ~0.4 GB of headroom is not enough for a run that
allocates past its budget.

## What the context changes for the user

- **Time to first token does not move.** Fill was 11.2 s at 32K against 11.2 s at
  512 for the same 53-token prompt: the fill is the expert tier, not the context.
- **The decode does not move either**, as long as the slab survives.
- **The prompt does.** Prefill runs at the fill rate, ~4.4-4.7 tok/s (measured
  through `llama-server`). A 500-token prompt is ~110 s to first token, 4,096 is
  ~15 min, and a 32K prompt is ~2 h. This is the practical limit on context for
  anything interactive, well before the VRAM problem.

## The HTTP path: `llama-server` with the bridge

The project's own server *is* this binary. `sabah serve` inspects the model and
then spawns the pinned, patched `llama-server` with the experts on the host and
`GGML_OP_OFFLOAD_MIN_BATCH=1` (`sabah/server/openai_proxy.py:252-280`). So a
client needs no special path â€” it needs that backend plus the placement flags.
The bridge lives in `ggml-cuda`, so the server loads it the same way the diag
does:


Measured through `POST /v1/chat/completions`, with **no diagnostic file set**:

| configuration | prompt eval | decode | request wall |
|---|---|---|---|
| `-c 32768`, `-ub 8` | 58 tok in 12.36 s = 4.69 tok/s | 31 tok in 5.82 s = **5.16 tok/s** (194 ms/token) | 18.2 s |
| `-c 8192`, default ubatch | 58 tok in 11.94 s = 4.86 tok/s | 30 tok in 5.73 s = **5.06 tok/s** (197 ms/token) | 17.7 s |

That is the diag driver's own rate at this length (`sabah run --tokens 32`,

These are **warm-up** numbers, not the steady state, and they must not be read

### The served path always sets a diagnostic, and it is not free

`openai_proxy.py:273` sets `SABAH_LLAMA_STATUS_FILE` unconditionally for the
`sabah` backend, and the runtime rewrites that file after every expert call â€” 144
of them per token. `docs/BENCHMARK_METHOD.md` prices that at ~0.3 s per token.
The same two configurations above, run *with* the status file set, report
**2.04-2.53 tok/s** instead of 5.06-5.16:

| configuration | decode with the status file | decode without it |
|---|---|---|
| `-c 32768`, `-ub 8` | 31 tok in 14.68 s = 2.04 tok/s | 31 tok in 5.82 s = 5.16 tok/s |
| `-c 32768`, `-ub 8`, 8-token request | 8 tok in 2.77 s = 2.53 tok/s | â€” |

This is the same trap the harness was fixed for (see `CHANGELOG.md`, "the harness
no longer poisons its own timings"); the proxy still has it. Any latency taken
through `sabah serve` today is roughly half the real rate at short lengths. It
does not affect correctness, and the counters it buys are exact.

Two more things about the served path, measured while writing this:

- **`sabah serve` did not come up on this artifact at all.** It needs a `gguf-py`
  that knows the artifact's quant type (`qwen4exp` uses type 42; the PyPI `gguf`
  raises `np.uint32(42) is not a valid GGMLQuantizationType` â€” point
  `SABAH_GGUF_PY` at the pinned tree's `third_party/llama.cpp/gguf-py`), and with
  that fixed it then failed on the Python side before any backend started:
  `pinned warm alloc 704000 B failed: cudaHostAlloc: out of memory` from the
  warm-RAM tier planner, on a rig whose 15.38 GiB of host RAM is largely in use.
  Neither failure is about this note's subject; both mean the numbers above come
  from `llama-server` directly, which is the same backend the proxy spawns.
- **`sabah serve` has no ubatch knob.** `--context 32768` with the default slab

One integration note: this is a reasoning model, and the server's default
template puts the chain of thought in `choices[0].message.reasoning_content`.
With a small `max_tokens` the `content` field comes back empty because the answer
never left the reasoning block. A client must read both fields and budget tokens
accordingly.

===== docs/CUDA_GRAPH_SPLIT.md (pass 1) =====

# Splitting CUDA graphs at the Sabah bridge

`ggml_backend_cuda_graph_compute` captures a whole `ggml_cgraph` or nothing, and
the compatibility check refuses the whole graph as soon as one `MUL_MAT_ID` is
Sabah-owned (the bridge reads the routed ids on the host, exactly like the
synchronizing `MUL_MAT_ID` fallback). With 48 blocks that means no graph at all:
2556 nodes and 144 Sabah calls are submitted one launch at a time, every token.

The split path captures the *other* nodes instead. It walks the graph, and:

* at a Sabah node: run it eagerly (the bridge waits for the stream itself), then
  continue with the next segment;
* between two Sabah nodes: capture that maximal run of nodes once, keep the
  `cudaGraphExec_t` keyed by the first node pointer, re-capture when any node's
  tensor or source pointer/shape changes, and replay it with one
  `cudaGraphLaunch` per token.

Stream order is preserved: launch segment 0, eager gate/up (which reads the
router ids), launch the next segment, eager down, and so on. The cost that the
split introduces is exactly one stream wait per Sabah call, which the bridge
already needed to read the ids.

## Knobs

| env | meaning |
|---|---|
| `SABAH_CUDA_GRAPH_SEG=<layers>` | enable for the first `<layers>` blocks (one block = 3 Sabah nodes). `0`/unset = off. `48` = whole model. |
| `SABAH_CUDA_GRAPH_SEG_STATS=1` | print the host-side split at exit |
| `GGML_CUDA_OP_TIMES=1` | per-node GPU time for the dense path (item 5); routes the whole graph through the plain node loop and syncs once per token |

`SABAH_CUDA_GRAPH_SEG_STATS=1` prints one line:

```
SABAH_SEG calls=N launches_per_token=.. captures=.. eager_per_token=..
  | host ms per token: launch=.. capture=.. eager=..
  | per launch us=.. per eager us=..
```

`launches_per_token` is the number of `cudaGraphLaunch` calls per decode token,
`eager_per_token` the number of nodes (Sabah and split fallbacks) run outside a
graph, and `per eager us` includes the stream wait the bridge performs.

## Bit-exactness

Replaying a captured segment runs the same kernels with the same arguments, so
the outputs must be byte-identical to the eager path. `tools/graph_poc.py`
checks this by running eager, one-layer and all-layer variants and comparing
`fed.i32`, `argmax.i32` and `logits.f32` with `tools/compare_runs.py`.

## Why one layer first

The PoC measures three costs before committing to all 48 blocks: the per-launch
host cost, the per-Sabah-call wait, and the capture cost when properties change.
If one layer's saving, multiplied by 48, does not project to at least 8 ms per
token, the split is not worth the extra states it adds to the backend.


===== docs/DECODE_BUDGET.md (pass 1) =====

# Decode cost budget (measured)

Rig: RTX 5060 Ti 16 GB, 15.38 GiB host RAM, NVMe. Model
`Qwen3.8-Flash-Next` IQ3_S (83.6 GB, 2 shards), 48 blocks x 512 experts,
top-10, expert bank 50.29 GB / 24576 objects.
Tool: `llama-sabah-diag`, `--cpu-moe -ngl 99`, direct I/O on, IO depth 8.
`SABAH_LLAMA_HOT_BYTES=9.8e9`.

## What a generation actually costs: fill, warm-up, steady state

The number this project used to quote - "206 ms/token, 4.84 tok/s" - is the
marginal token of a generation that has just started, because it comes from
differencing short runs (`-n 32` minus `-n 8`, i.e. decode steps 9..32). A long
run prices the whole shape. Same prompt, same binary, only `-n` differs, and the
token stream is the model's own greedy tokens in every case:

| run | prefill | decode median | decode mean | decode sum | disk reads | disk GB | wall |
|---|---|---|---|---|---|---|---|
| `-n 1` (prefill only) | 11446 ms | - | - | - | 20087 | 12.68 | 20.1 s |
| `-n 128` | 11186 ms | 79.3 ms | 123.9 ms | 15.9 s | 34019 | 21.43 | 35.9 s |
| `-n 256` | 11156 ms | 70.1 ms | 96.2 ms | 24.6 s | 34598 | 21.81 | 46.1 s |

Differencing gives the three regimes exactly:

| regime | reads | bytes | per token | cost |
|---|---|---|---|---|
| **cold fill** (the 53-token prompt) | 20087 | 12.68 GB | - | **11.2-11.5 s, 1.11 GB/s** |
| **warm-up** (decode steps 1..127) | 13932 | 8.75 GB | 109.7 reads | 70.6 MB/token |
| **steady state** (steps 128..255) | 579 | 0.38 GB | **4.5 reads** | **3.0 MB/token** |

Step times by window (from a 257-step run) show the settling:

| steps | 1-32 | 33-64 | 65-96 | 97-128 | 129-160 | 161-192 | 193-224 | 225-256 |
|---|---|---|---|---|---|---|---|---|
| median ms | 203.9 | 122.4 | 72.2 | 71.5 | 68.3 | 68.4 | 67.5 | 66.9 |

So the machine does three different things, and averaging them into one tok/s
number hides all three:

* **Time to first token: ~11.2 s.** The prompt is 53 tokens; the 11 s is not
  prompt processing, it is the expert tier's **cold fill** - 12.68 GB of expert
  bytes at 1.11 GB/s. Nothing about the prompt is hard; the tier starts empty.
* **Warm-up: the first ~128 decodes.** The tier finishes discovering its working
  set (70.6 MB/token of disk), which is why the decode median is 204 ms at step
  32 and 79 ms at step 128.
* **Steady state: ~67 ms/token = ~15 tok/s, effectively disk-free** (4.5 reads,
  3.0 MB per token). After ~130 tokens the tier holds the working set and the
  disk is no longer on the critical path at all.

End to end, a 256-token answer costs 11.2 s + 24.6 s = 35.8 s, **7.1 tok/s
including the fill**, 10.4 tok/s over the decodes alone, and 15 tok/s once warm.
Which of those is "the" number depends entirely on whether the workload is one
long answer (steady state matters) or many short ones (the fill is paid every
time and dominates).

The same three regimes explain what each lever can buy, and the rest of this
document is per-regime:

| lever | cold fill | warm-up | steady state |
|---|---|---|---|
| a faster disk (lever 1) | **11.2 s -> ~3 s at 6 GB/s** | partially | nothing (already disk-free) |
| a bigger/second tier (lever 5) | cuts the bytes that miss | cuts the bytes that miss | nothing |
| batching (lever 3) | - | - | **the only thing that helps** |
| the floor itself (lever 4) | - | - | **it *is* the steady state** |

## Where a decode token goes during the warm-up

Isolated by differencing two runs of the same binary (`-n 32` minus `-n 8`,
so the prefill cancels out) minus the phase totals. **This prices decode steps
9..32, i.e. the warm-up, not the steady state** - see the section above for why
that distinction matters:

| phase | per token | notes |
|---|---|---|
| `fetch` disk reads + H2D | **121.8 ms** | 164.5 MB/token over 247.4 reads = 1.35 GB/s, at the drive's ceiling |
| `ids` router download + stream drain | **29.3 ms** | one drain per layer, 3 calls share it |
| `slot` residency bookkeeping | **9.3 ms** | 239 evictions/token, ~39 us each |
| `ptr` pointer table upload | **1.5 ms** | |
| `prime` residency snapshot | **1.3 ms** | |
| outside the bridge (graph, launch, host-side ops) | **27.7 ms** | residual: phases sum to 163.2 of 190.9 |
| **decode wall (sum over 24 tokens / 24)** | **190.9 ms** | decode *median* 205.7 ms |

By step 96 the same sum is **~70 ms**, and the disk portion of it is ~3 MB. The
tier is the whole story of the first two regimes; the floor is the whole story of
the third.

## The binding constraint is the disk, at ~1.2-1.5 GB/s - while it is on the path

The tier's cold fill must come off the disk, and the effective unbuffered rate in
this access pattern (random 676 KB blocks across an 83 GB file) is **~1.1-1.5
GB/s**, and **adding concurrency does not raise it**: this drive gains ~15% from
one reader to sixteen. The isolated probe's 2.5 GB/s at QD 8 is over *sequential*
1 MB reads, which is a different access pattern; its *random* 676 KB case quoted
2.4-2.5 GB/s only because it re-read one offset list, and drawn fresh that case is
worth ~1.1-1.45 GB/s (see "Lever 2" below).

So every byte the tier has not yet learned costs ~0.7 ms/MB, and a 12.68 GB cold
fill costs ~11 s before the model can answer anything.

## Raising the slab

| slab | hits/misses | decode bytes/run | tok/s | peak VRAM |
|---|---|---|---|---|
| 9.0 GB | 90653 / 28747 | 19.41 GB | 4.16 | 14566 MiB |
| 9.8 GB | 91285 / 28115 | 18.97 GB | 4.37 | 15356 MiB |

+0.8 GB buys ~2% fewer bytes. VRAM is essentially exhausted (16.31 GB card,
non-slab footprint ~5.4 GB).

## What was optimised, and what it bought

| change | cost before | after | tok/s |
|---|---|---|---|
| baseline (per-call drain, linear erase) | ids 87 ms | | 4.37 |
| router ids reused across a layer's 3 tensors | 87 ms | ~23 ms | 4.75 |
| single-scan residency memo per call | | | 4.79 |
| swap-and-pop eviction instead of `vector::erase` | slot 30 ms | ~11.5 ms | **4.84** |

The last two are the same two ideas the plan called for (per-layer id drain,
cheaper residency): together **4.37 -> 4.84 tok/s (+11%)**, still zero mapped
fallbacks, RAM flat at 4.78 GiB, peak VRAM 15.36 GB.

### Router id reuse

The three expert tensors of one MoE layer (`gate`, `up`, `down`) read the *same*
`selected_experts` tensor, so two of the three `cudaStreamSynchronize` per layer
are redundant. The bridge passes `dst->src[2]` (the ids ggml_tensor address) so
the runtime can tell "this is the same tensor as the call before" and skip the
copy and the drain. Groups are capped at `SB_ID_GROUP_MAX=4` calls, and that cap
is also the width of the eviction-protection window: entries from the last
`SB_ID_GROUP_MAX` epochs are never chosen as victims, which is what makes it safe
to free a slot while a kernel enqueued before the last drain may still read it.

*Proof:* `SABAH_LLAMA_ID_CHECK=1` forces every download anyway and compares the
reused bytes with the fresh ones: **`check_ok=3072 check_fail=0`**.
*Byte-exact:* with reuse active, `SABAH_LLAMA_VERIFY_BYTES=fetch
SABAH_LLAMA_VERIFY_LIMIT=500` gives **`verify_ok=500 verify_fail=0`**.

Removing the drains exposed a latent race: the pointer table is ONE device
buffer that every call rewrites, and the H2D used to go on the copy stream. The
per-call drain had been providing the ordering implicitly. The upload now runs on
the compute stream, so it is ordered after the kernel that is still reading the
same buffer. (A run with the racy order reported 9.90 tok/s and 23% fewer bytes;
those counters are not reproducible and that run must not be trusted.)

## Staging readahead (`SABAH_LLAMA_PREFETCH=1`, default off)

Shape: the prefetcher reads the *following* calls' experts into pinned staging and
leaves them there; the demand path copies them to their device slot and never
touches the disk. It reserves no tier space - an earlier shape that did reserve
made the demand path read its own reserved-but-unfilled slot a second time and
cost 2.8x the bytes (1.48 tok/s vs 4.16).

Two facts are learned rather than assumed:
* The call chain is keyed by the **expert tensor** address. Keying it by the
  router ids tensor was wrong: the graph allocator hands every layer the same
  address for that buffer, so the chain collapsed into one node claiming all 144
  tensors and the prefetcher pulled the whole bank (98% of bytes wasted).
* Whether the following call reuses the ids is learned by comparing the ids this
  call downloaded with the previous call's.

Correctness: the tier's `hits`/`misses`/`evictions` are **identical** to the
prefetch-free run, so the prefetch only moves bytes, never residency. Cost:
~8 x 2.7 MB extra pinned staging (~22 MB).

It does not pay: with the disk at ~1.3 GB/s and the demand path already able to
keep several reads in flight, moving bytes off the critical path changes nothing
(4.04-4.06 vs 4.16 at the time), and 40% of the readahead is superseded before
anyone asks for it (`stale=2313` of 5699). It becomes worth revisiting only if
the disk time drops below the bookkeeping time, which needs a bigger tier first.

## Lever 2, closed: the demand path is already at the drive's rate

The second lever in the plan was "close the exposure gap, 1.31 GB/s -> ~2.4 GB/s
in the demand path". The gap is not there. The ~2.4 GB/s target came from a
benchmark that - unintentionally, but unavoidably as it was written - re-read the
same offsets, and this drive serves a repeated read about 1.5x faster than a
fresh one. A fresh random 676 KB read workload is worth ~1.1-1.45 GB/s on this
hardware at any depth, and that is what the runtime already achieves.

**The drive, with fresh offsets every run** (`tools/io_bench.cu`: 676 KB reads -
the expert stride - 800 requests, whole repository file, pinned staging,
`FILE_FLAG_NO_BUFFERING`):

| readers in flight | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| fresh offsets, pass A | 1047 | 1136 | 1127 | 1196 | 1220 MB/s |
| fresh offsets, pass B | 1152 | 1293 | 1372 | 1457 | 1458 MB/s |
| **the same offsets re-read** | 1148 | 1617 | 1814 | 1809 | 1797 MB/s |

Rows two and three are back-to-back runs on the same drive; the only difference
is whether the offsets repeat. Any benchmark that draws one offset list and
reuses it - which is what `tools/disk_probe.py` did, for every queue depth it
reported - therefore quotes a number the demand path can never see, and that is
where the 2.4-2.5 GB/s in this document and in `LOCALITY_FINDINGS.md` came from.
`disk_probe.py` now redraws its offsets per case.

Nothing else moves the number: pageable vs `cudaHostAlloc` staging (the
allocation itself costs ~70 ms per process, which is the whole of the MB/s
difference), `FILE_FLAG_RANDOM_ACCESS` or not, and offsets clustered per wave
inside a moving 600 MB window - a layer's ten experts all live in one ~600 MB
tensor region, so this is the runtime's real locality - vs spread over the whole
file.

**What the runtime does with it.** Every configuration below reads the same
18.97 GB for the same run (`-n 32`, one shard, direct I/O):

| configuration | whole-run unbuffered time | decode median | `SABAH_IO overlap` |
|---|---|---|---|
| one overlapped file object, depth 1 / 8 / 32 | 1.42 / 1.35 / 1.35 GB/s | 205.9-207.7 ms | - |
| one synchronous lane behind each wave | 13713.9 ms | 205.8 ms | 1.00 |
| two lanes | 13663.7 ms | 203.1 ms | 1.78 |
| eight lanes | 13734.0 ms | 204.5 ms | 3.84 |
| eight lanes + merged layer fetch | 13657.0 ms | 218.0 ms | 4.22 |

`overlap` is the sum of the individual `ReadFile` durations divided by the wall
time the caller spent inside the waves, reported by `SABAH_IO`. At eight lanes
the reads really are four deep on average - the read calls sum to 52.8 s against
13.7 s of wave time - and the run is **not one millisecond faster** than the
one-lane run where they are strictly serial. That is the expected result now that
the drive's own curve is known: it gains ~15% from one reader to sixteen, so
~1.2-1.45 GB/s is what this access pattern is worth, and the runtime reads at
1.38-1.46 GB/s. It is at the top of the curve, not short of it.

The same reasoning retires the merged layer fetch (one wave per layer instead of
three, `SABAH_LLAMA_LAYER_MERGE`, default off): it halves the wave count exactly
as predicted, decode 99.9 -> 49.5 waves/token and prefill 5664 -> 4088, and the
time does not move by a millisecond, because the half of `fetch` that is not
transfer is not a per-wave charge on this drive. It is a net loss - concentrating
the layer's wait into one call leaves the GPU idle for a longer stretch, which
the next group's router drain then exposes - hence ~205 ms without it against
~218 ms with it. It stays in the code, defaulted off, because it is the shape
that would pay off on a wave deep enough for depth to matter.

**Current decode budget** (re-measured, same method: `-n 32` minus `-n 8`):

| phase | per token | notes |
|---|---|---|
| `fetch` disk reads + H2D | **121.8 ms** | 164.5 MB/token over 247.4 reads = 1.35 GB/s, at the drive's ceiling |
| `ids` router download + stream drain | **29.3 ms** | one drain per layer, 3 calls share it |
| `slot` residency bookkeeping | **9.3 ms** | 239 evictions/token, ~39 us each |
| `ptr` pointer table upload | **1.5 ms** | |
| `prime` residency snapshot | **1.3 ms** | |
| outside the bridge (graph, launch, host-side ops) | **27.7 ms** | residual: phases sum to 163.2 of 190.9 |
| **decode wall (sum over 24 tokens, / 24)** | **190.9 ms = 5.24 tok/s** | decode *median* is 205.7 ms; the tier keeps warming for ~50 tokens |

The same run's cache counters, which the trace line does not carry (`-n 32`
minus `-n 8` from the runtime's status JSON, a separate pass because
`SABAH_LLAMA_STATUS_FILE` rewrites a file on every call and inflates any timing
it touches):

| counter | per token | notes |
|---|---|---|
| calls | 144 | 48 layers x 3 tensors |
| lookups | 1440 | 10 experts x 144 |
| hits | 1192.6 | |
| misses | 247.4 | one 635 KB read each: 156.9 MB |
| evictions | 239.0 | the tier is full, so admissions evict almost 1:1 |
| overflow | 22.0 | eviction attempts that found only epoch-protected victims |
| resident | 9.13 GB of a 9.8 GB budget | cumulative hit rate 76.7%, marginal 82.8% |

Two passes of the identical configuration differ by ~5% in bytes/token (164.5 vs
156.9 MB); the miss *count* is stable (247.4 in both). Treat 5% as the noise
floor of this method.

Byte-exact after all of it: `SABAH_LLAMA_VERIFY_BYTES=1` gives
`verify_ok=64191 verify_fail=0` with the same 28114 reads, the same
18968409600 bytes and zero mapped fallbacks.

So the disk is 64% of the token and it is already reading at the rate this drive
serves this pattern. The remaining levers are "fewer bytes" (a bigger tier) and
the 67 ms of non-disk work, which is now measured rather than "unprofiled" (next
section). **Lever 1 stays real but its projection must be re-measured with fresh
offsets**: "174.7 MB at 6 GB/s = 29 ms" assumed the probe's repeat-read ceiling
scaled linearly onto a faster drive. With the floor below, the honest projection
is `157 MB / GB/s + 67 ms` instead of a byte count alone.

## The no-disk floor: what a perfect cache would still leave (lever 4, closed)

The diag can run several prompts in one process, clearing the KV between them but
**leaving the expert tier warm**. Feed the same forced token stream to every item
and the items after the first re-touch exactly the same `(tensor, expert)`
objects, so their disk demand collapses to nothing. Measured that way, with a
working set far under the tier (4-token prompt, 8 forced tokens, 6 items), items
2..6 read **0 bytes** and cost:

| positions per call (B) | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| pass wall (ms) | 67.3 | 99.1 | 156.8 | 278.8 |
| **per position (ms)** | **67.3** | **49.5** | **39.2** | **34.9** |

Fitted: `floor(B) ~ 30.3 + 37.0 / B` ms per position. The `30.3` is per-position
work (the expert arithmetic itself: ~1 GB of IQ3_S expert weights per token must
be read out of VRAM and dequantised); the `37 / B` is per-call cost, and it is
dominated by the per-layer router drain, not by residency: in the same shape at
B=1 the phase totals differenced across item counts give `ids ~50 ms/token` and
`ptr + prime ~1.8 ms/token`, with `slot ~0` (no evictions in a small working
set). The remaining ~15 ms is outside the phases: llama.cpp's graph walk, kernel
launches, and the per-step logits read the diag performs.

**This is the whole non-disk cost, and a long generation confirms it from the
other direction.** Two independent measurements land on the same number: this
replay, which removes every byte of disk traffic, costs 67.3 ms/token; and the
last 128 decodes of a 256-token generation, which read 3.0 MB/token, cost
67-68 ms/token. **The runtime's steady state is exactly its floor**, which also
means the steady-state rate cannot be improved by any storage change at all.

During the warm-up the two are additive: the measured 190.9 ms/token is
121.8 (disk) + 69.1 (everything else), agreeing to 1% with the replay. If the
runtime overlapped the drive with its own work there, the token would be
`max(121.8, 67.3) = 121.8 ms` instead of their sum. It does not, and that is
what the readahead section above is about.

Why it cannot be fixed by re-ordering:

* The dependence is real: layer L+1's router input is layer L's expert output, so
  the ids for L+1 cannot exist before L's kernels have run. One drain per layer
  is the floor for this design, and batching is the only thing that amortises it
  (`37/B` above, and `ids` 29.3 -> 11.9 ms/token from B=1 to B=8 in the
  verification probe).
* The drive is the bottleneck and its bandwidth is fully priced, so reads issued
  early are worth exactly what reads issued on demand are worth. Staging
  readahead therefore only pays with a near-perfect predictor, and the one that
  exists is 40% stale (`SABAH_LLAMA_PREFETCH`, section above), which is why it
  measured neutral-to-worse.

What this bounds, per regime (the numbers are per token of the regime named):

| change | warm-up token becomes | steady-state token becomes |
|---|---|---|
| today | 190.9 ms | 67 ms |
| perfect cache, zero disk traffic | 67.3 ms | 67 ms (already there) |
| a 6 GB/s drive | ~93 ms | 67 ms |
| a 3 GB/s drive | ~119 ms | 67 ms |
| any tier that removes 45% of the reads | ~124 ms | 67 ms |

And for the cold fill, which no batching or floor work touches:

| fresh tier | 12.68 GB cold fill at |
|---|---|
| today (1.11 GB/s measured) | 11.4 s |
| 3 GB/s | 4.2 s |
| 6 GB/s | 2.1 s |

So: no storage lever can change the steady-state decode rate - it is already the
floor - and the fill is paid once per fresh working set. Storage levers buy *time
to first token* and the warm-up, and the steady state needs the *demand or the
floor* to change, which is what levers 3 and the floor curve above are about.

## The floor, split by device (Phase 0, measured)

The floor above (67.3 ms/token) was measured as a total, on an earlier binary.
On the current one the same method gives a lower total, and the split is what
matters. Steady state on the README configuration is now **58.59 ms median over
127 decodes (17.07 tok/s)**; an Nsight Systems capture of a warm replay puts
**43.3-43.7 ms on the GPU (74%)** and leaves **15.2 ms** with the host. The
method above is unchanged; this section supersedes the split, not the method.

| per steady token | ms | kernels/token |
|---|---|---|
| Sabah `gate`+`up` | 17.1-18.0 | 96 |
| dense matmul (llama.cpp) | 12.4-12.8 | 752-770 |
| Sabah `down` | 9.6-10.0 | 48 |
| elementwise / router | 2.45-2.51 | 2,494-2,556 |
| PLE / embedding | 0.42 | 93-98 |
| SSM | 0.23 | 70 |
| attention | 0.11-0.12 | 55-60 |
| **GPU busy** | **43.3-43.7** | **3,662-3,756** |
| host, additive | 15.2 | - |

The Sabah kernels are 27.1-28.0 ms of that 43.4 (62%): 144 calls, ~1.01 GB of
expert weights per token, ~37 GB/s effective. The trace also shows ~80
`cudaStreamSynchronize` per token (2.6-2.8 ms) and 6.4 ms idle gaps between the
three expert kernels of a layer when a miss occurs - the host round trip, visible.

The host 15.2 ms is launch submission, priced directly (`tools/launch_latency.cu`,
4,000 samples per case, WDDM): **3.42 us per empty-kernel submission with the GPU
busy, 5.61 us idle**, 6.2 us for a 64 B D2H plus its sync. Schedule policy
(`cudaDeviceScheduleSpin` vs auto) and `THREAD_PRIORITY_HIGHEST` change nothing
(3.61 us busy, 812 us per simulated 48-step token, both within noise).

| item | per token |
|---|---|
| 3,756 kernel submissions x 3.42 us | 12.85 ms |
| 48 router-id drains (D2H + sync) | 0.30 ms |
| residual (memcpy submissions, graph walk) | ~2.0 ms |
| **sum** | **~15.2 ms** |

Two things follow, and they are the Phase 1/2 split:

* The host does not overlap the GPU, it adds to it: 58.6 = 43.4 + 15.2, not
  `max(43.4, 15.2)`. The per-layer router drain empties the queue 48 times per
  token, and after each drain ~78 launches have to be re-submitted while the GPU
  waits - ~265 us per layer at 3.4 us/launch, ~12.7 ms per token.
* Launch **count** is the cost driver, not launch price. Elementwise/router is
  2,556 launches (68% of all launches) for 2.5 ms of GPU work; submitting them
  costs ~8.7 ms of host time.

So removing the exposed submission (a queue that stays deep, or a device-side id
path) is worth 58.6 -> 44.4 ms = 22.5 tok/s on its own. It is also a precondition
for a kernel win: halving Sabah's 27.3 ms removes 13.65 ms, which lands at
44.95 ms (22.2 tok/s) with the host gap still additive but at 30.75 ms
(32.5 tok/s) once the queue stays deep. The two are multiplicative.

The dense matmul is already bandwidth-bound: the non-expert matmul weights on
CUDA0 are 3,979 MiB, read once per token, so 4.17 GB in 12.6 ms = **331 GB/s,
74% of the card's 448 GB/s**. Its header is 3.3 ms, and the lever there is more
positions per weight read, not a faster kernel.

## Lever 3, closed: batch verification and speculative decoding are dead here

The plan's "fewer bytes per token" was speculative decoding, on the theory that
offline analysis had shown the union of experts touched by a batch of 4 tokens to
be 676 MB/token against 982 MB for four sequential tokens - 31% less demand. That
number does not survive contact with the tier.

Measured cost of a *100%-acceptance* verification pass (the diag feeds the
baseline's own greedy tokens in groups of B as one `llama_decode`, so every
position is one a verifier would accept, and nothing is drafted or rolled back):

| B | pass wall | pass bytes | pass reads | ms/position | MB/position |
|---|---|---|---|---|---|
| 1 (sequential) | 190.9 | 164.5 | 247.4 | 190.9 | 164.5 |
| 2 | 339.8 | 330.9 | 497.6 | 169.9 | 165.4 |
| 4 | 648.8 | 669.7 | 1006.3 | 162.2 | 167.4 |
| 8 | 1290.8 | 1356.9 | 2037.7 | 161.3 | 169.6 |

Two things fall out. The best case is **15% faster per position** (B=8: 161.3 vs
190.9) and it comes entirely from amortising per-call overhead - `ids` 29.3 ->
11.9 ms/token, `waves` 96.5 -> 40.6 - not from fewer bytes. Bytes per position get
slightly *worse* with B (164.5 -> 169.6 MB), so the union figure was about cache
residency demand, not about what the tier actually misses.

Break-even, from the pass costs: with `P` passes per token and `A` the acceptance
rate, verification wins only if `A > (P * pass_cost / sequential) - 1`. At B=2
that is 78% of the 1 drafted token, at B=4 80% of 3, at B=8 82% of 7 - and that
ignores the re-decode a rejection costs, which pushes the real requirement to
85-90%.

The acceptance rate on this machine's own greedy stream, simulating upstream's
`common_ngram_simple_draft` exactly (n-gram size 2-6, 2-8 drafts per pass, over
256 tokens): **0.004 accepted drafts per pass at best, 99.6% of passes accept
nothing at all, and n >= 3 accepts literally never.** The prompt and the
continuation do not repeat token sequences, and that is what n-gram drafting
needs. Converting the measured pass cost to yielded tokens, including the
rejection re-decode:

| B | ms/token | vs sequential | MB/token | vs sequential |
|---|---|---|---|---|
| 2 | 528.7 | 2.77x slower | 493.4 | 3.00x |
| 4 | 836.5 | 4.38x slower | 830.9 | 5.05x |
| 8 | 1475.9 | 7.73x slower | 1515.4 | 9.21x |

Speculative decoding with this drafter costs 2.8-7.7x. It is not marginal, it is
not close, and the mechanism is not fixable by tuning n or m: the drafter's whole
premise is absent from the text this model is being asked to produce. A trained
drafter would change the arithmetic, but then B=8 has to accept 82% of seven
tokens, i.e. it needs to be right about the model's own greedy output almost
every time.

**What is not dead is batching itself.** The floor curve above says B=8 costs
34.9 ms/position against 67.3 at B=1 - 28.7 tok/s, and that is the number that
matters for the steady state, which no storage change can touch. Speculation is
one way to get a batch; *concurrent requests* are another, and a server does not
need to predict the model's own output to have them. `SABAH_DIAG_MULTISEQ` and
`n_parallel` exercise that path today. Two caveats before quoting 28.7 tok/s:
the probe's batch was one sequence's own tokens (so its expert sets were drawn
from a shared context, which is the friendlier case for the tier), and the
steady-state demand of N unrelated prompts is not measured here. The 34.9 ms
floor is solid; the disk part of a real concurrent batch is not.

## Can a bigger tier or "virtual RAM" get to 10-15 tok/s?

It already does, once warm: **15 tok/s is the steady state today**. What a bigger
tier buys is the *fill* and the *warm-up*, not the sustained rate. Byte
requirement: the warm-up demands ~833 MB/token of *distinct* expert bytes if
nothing is cached; cached bytes are free (they are already in VRAM); every
*uncached* byte costs 1/1.4 GB/s. The measured floor (67.3 ms) is **added** to the
disk time during the warm-up (it is not overlapped), so it appears in the wall
column:

| effective tier | hit rate | bytes/token in the warm-up | disk time | warm-up wall = disk + 67.3 ms | cold fill |
|---|---|---|---|---|---|
| 9.8 GB (today) | 82.8% | 110 reads/token (measured) | ~70 ms | ~140 ms (measured mean 124-96) | 11.4 s |
| 15.9 GB | 92.5% | ~48 reads/token | ~31 ms | ~98 ms | ~5 s |
| 27 GB | ~93% | ~45 reads/token | ~29 ms | ~96 ms | ~1.5 s |
| no disk at all | 100% | 0 | 0 | 67 ms (the floor) | 0 |

The hit-rate column is the measured LRU curve in
[`LOCALITY_FINDINGS.md`](LOCALITY_FINDINGS.md) (10.64 GB 86.4%, 15.96 GB 92.5%),
not an extrapolation.

- 15 tok/s is reachable today **once warm**, and nothing about the tier changes
  that: the floor is 67 ms/token and the steady state is already there.
- 10 tok/s over a *short* answer is the real target to aim at, and it is a
  **fill** problem: 12.68 GB at 1.11 GB/s = 11.4 s. A tier that is already warm
  across requests (a server, or a second tier in host RAM) is what removes it; so
  is a faster drive.
- 30 tok/s is reachable only by batching: `floor(B) = 30.3 + 37/B` puts B=8 at
  34.9 ms/position = 28.7 tok/s. Nothing else in this document moves the steady
  state.

**Virtual memory does not help.** Windows "virtual memory" is the page file, which
lives on the same NVMe, so bytes served from it cost the same ~1.3-1.6 GB/s and
arrive through the page-fault path instead of a 676 KB unbuffered read at QD 8 -
strictly worse, and it cannot be prefetched with a controlled queue depth. It can
only add *capacity*, and capacity is not the problem for the steady state: the
tier already holds the working set once warm.

The thing that *would* be fast is the OS page cache (RAM reads at ~10 GB/s), and
that is exactly what was ruled out: the expert path uses `FILE_FLAG_NO_BUFFERING`
precisely so host RAM stays free. Relaxing that constraint is the one change that
would move the needle on the *fill* - a host-RAM expert tier would serve the
warm-up's demand from RAM instead of disk, and the path is measured: **0.047 ms
per expert round trip through pinned host memory, 13.9 GB/s**
(`tools/second_tier_probe.cu`, see [`SECOND_TIER.md`](SECOND_TIER.md)). That is
9.6x cheaper than the disk's 0.45 ms, worth ~1.5x on the warm-up and nothing on
the steady state. It remains a decision about the RAM budget, not an optimisation,
and this project targets RAM-constrained machines.

### The exactness argument, in three tests

1. **Decode.** All four expert quant types produce `max|diff| = 0.000e+00`
   against `gguf.quants.dequantize`, on bytes taken out of the user's own
   artifact. The device test recovers each element by dotting the sub-block
   with a unit vector, so it exercises `sub32_*` - the code the matvec kernels
   call - rather than a parallel implementation that could be right while the
   kernels are wrong.
2. **Execution.** A full block agrees with a numpy reference to 6.0e-07
   relative L2. The same comparison with one routed expert swapped gives
   4.7e-01. A test that cannot detect a wrong expert cannot certify a right
   one, so that second number is part of the pass criterion.
3. **Residency independence.** Same block, same ids, run resident and again
   after forced eviction and refetch: bit-identical. This is what makes the
   cache legitimate rather than merely fast.

### Measured (block 0, real trace, 1000 tokens)

```
slots  hit      ms/tok   gpu stall  host stage   fetched
   16  0.0765    4.646      0.223       3.759    28.4 MB    mmap bank
   64  0.3091    3.377      0.203       2.569    21.2 MB
  256  0.8410    1.520      0.061       0.551     4.9 MB
  512  1.0000    1.274      0.000       0.000         0     <- kernel only

   16  0.0765    2.879      1.407       0.000    28.4 MB    pinned RAM bank
   64  0.3091    2.186      0.905       0.000    21.2 MB
  256  0.8410    1.330      0.061       0.000     4.9 MB
```

### Two findings

**1. With an mmap bank the bottleneck is the host, not PCIe.** 81% of the time
at 16 slots (3.759 of 4.646 ms) is the CPU copying page-cached bytes into
pinned staging; the GPU waits 0.223 ms. This was measured directly, not
inferred by subtraction - the staging copy is timed in
`hot_tier._fetch_async`. Staging throughput works out to 7.5 GB/s, which for a
single-threaded read+write is already at the RAM roof.

The fix is not to thread the copy but to remove it: a pinned RAM bank is
DMA-readable in place. `ExpertBank(mode="ram", pinned=True)` plus the
`_direct` path in the hot tier deletes the copy and buys 1.6x at low
residency. With it gone the accounting closes - 1.274 ms kernel + 1.407 ms
measured stall vs 2.879 ms observed - and since 28.4 MB at the measured
12.76 GB/s would cost 2.22 ms, about 37% of the transfer is genuinely hidden
behind compute.

This also sharpens what the planner's `GPU_HOT_TIER` vs `STORAGE_BACKED`
distinction is worth: it is not just a hit-rate difference, it is whether the
staging copy exists at all.

**2. The planner was calibrated on the wrong policy.** v4's hit curve measured
a STATIC hot set. The runtime seeds by popularity and then runs LRU. Measured
on the same trace, same byte weighting, same capacity budget, LRU beats an
*oracle* static placement by 0.13-0.19 and the deployable one by 0.17-0.24.
The planner was under-predicting its own runtime by ~0.10 hit and refusing
machines it could serve.

Fixed: `HIT_CURVES['qwen4exp']` now carries `lru` (the operating point) and
`static_deployable` (the floor). The generalisation-gap subtraction was
removed from the LRU path - that curve is already measured on tokens the
warm-up window never saw, so subtracting it again would double-count. The low
end of every hot-tier projection is now the same model re-evaluated at the
static hit rate, rather than a flat percentage band.

### Bugs found during bring-up

1. **PTX JIT refused by the driver.** Default nvcc codegen for CUDA 13.3
   produced PTX the installed driver would not compile. Fixed by building for
   the detected architecture (`-arch=sm_89` here); the build instructions now
   derive it from `nvidia-smi` instead of hard-coding it.
2. **Measuring the stall created one.** `cudaEventElapsedTime` synchronises, so
   reading the compute-stream stall inside the loop serialised host and device.
   Replaced with a 512-deep ring of event pairs drained between runs.
3. **Staging reuse drained the whole copy stream.** Reusing a staging buffer
   called `cudaStreamSynchronize(copy)`, waiting on every in-flight transfer
   instead of that buffer's own. Each buffer now carries its own event. This
   alone took block 0 at 16 slots from 9.127 to 4.646 ms/token.
4. **Heredoc truncation.** Large source files written through shell heredocs
   were silently cut off mid-file, producing an unterminated heredoc rather
   than a syntax error. Switched to direct file writes for anything large.
5. Test entry points read `sys.argv[1]` even when called in-process, so the CLI
   subcommand name was interpreted as a model path.

# Known limitations

## Performance

- **The tested configuration is slower than stock llama.cpp.** v1.0 measured
  0.25Ã— stock decode throughput (0.411 vs 1.619 tok/s) on the validation
  machine: RTX 4050 Laptop 6 GB, ~30 GB RAM. The 77 GB expert bank does not
  fit in RAM, the expert tier is 1 GiB with a 46% hit rate, and every miss is a
  synchronous allocate/copy. No performance work was done for v1.0.
- No end-to-end speedup has been measured on any machine.
- Multi-GPU H2D aggregate, contention and fixed-path sharding are
  UNVALIDATED; all multi-GPU figures are PROJECTED.
- **Context and the expert slab compete for the same VRAM, and losing is an
  abort, not a slow token.** At `-c 32768` a 9.8 GB slab leaves ~0.4 GB of
  headroom; the tier's documented over-budget allocation then has no device
  memory to take, the call returns null and the process aborts (`0xC0000409`,
  reproduced 3 of 3). Measured working configurations â€” 32K with an 8.0 GB slab,
  or with `-ub 8` â€” are in [`docs/CONTEXT_VRAM.md`](CONTEXT_VRAM.md).

## Correctness scope

- Validated on one machine, one model (`qwen4exp`, Qwen3.8-Flash-Next
  UD-Q4_K_XL) and 14 + 4 preregistered prompts. The statistical gates use 14
  prompt clusters Ã— 32 teacher-forced steps. Gate I has ~0.79 power at its
  margin, and 14 clusters rule out only large differences in greedy flip
  propensity.
- Greedy output is not guaranteed to match llama.cpp token for token. Sabah's
  expert arithmetic is closer to float64 than llama.cpp's 8-bit-activation
  kernels, so greedy decoding can take the other branch at close calls. In
  validation this happened at 4 of 448 steps, vs 3 of 448 for llama.cpp's own
  CPU backend. One Sabah flip (`json_2`, step 2) was at a reference margin of
  1.35 logits, not a near tie.
- The full-graph comparison (gates H, I) was made on identically instrumented
  graphs. Observing tensors disables CUDA operator fusion across them, for the
  reference and for Sabah alike.
- llama.cpp's native CUDA Q5_1 down projection (MMQ path) deviates from float64
  by ~9e-3 beyond what its 8-bit activation quantization explains. The
  mechanism is not identified. Native CUDA is used only as a comparison anchor,
  never as an arithmetic oracle.

## Integration

- Only `qwen4exp` is accepted.
- Requires the pinned, patched llama.cpp (`96ffdc41c` + patches 0001/0002),
  CUDA and an NVIDIA GPU.
- Sabah executes decode steps only with `GGML_OP_OFFLOAD_MIN_BATCH=1`, which
  `sabah serve` sets. With llama.cpp's default (32), small batches run on the
  CPU and never reach Sabah.
- The HTTP path is `llama-server` with the bridge loaded â€” the same backend
  `sabah serve` spawns â€” but it was only exercised at 31-64 generated tokens,
  i.e. inside the warm-up regime, and `sabah serve` itself did not come up on
  this artifact (its `gguf-py` rejects the quant type, then the warm-RAM planner
  fails to pin host memory). See [`docs/CONTEXT_VRAM.md`](CONTEXT_VRAM.md).
- `--validate` (float64 self-check, byte verification) is much slower and is
  meant for verification, not use.
- The 77 GB expert bank does not fit in the validation machine's RAM; the
  storage-backed path is a correctness path, not a performance claim.

## Expert address mapping

For qwen4exp, the model loader establishes this logical mapping:

```text
llama block il
  -> blk.il.ffn_gate_up_exps / ffn_down_exps
  -> GGML tensor expert axis ne[2]
  -> expert e at byte offset e * nb[2]
  -> source GGUF shard/range owned by llama_model_loader
```

The exact byte offset must be taken from the loaded tensor's `nb[2]`, not from
an assumed constant. The scheduler already uses the same value at
`ggml-backend.cpp:1712-1713`. Sabah's `ExpertId(block, expert)` can represent
the logical key, but a native adapter still needs the tensor pointer, role,
quant type, row stride and source byte range for each role.

The following representatives are mandatory mapping tests before claiming an
integrated path: `(0,0)`, `(0,17)`, `(0,511)`, `(2,0)`, `(2,17)`, and
`(47,511)`, for every expert role present in that layer. The tests must verify
that layer, role, shard and `nb[2]` agree and that no cross-layer alias occurs.

## What is already proven versus what is not

Already proven in the Sabah repository:

- exact CUDA block arithmetic for the supported expert quant types;
- the Python `HotTier` LRU, eviction/refetch and telemetry in the standalone
  block path;
- real llama.cpp loading and reference generation for the target GGUF.

Proven by the current integration run:

- the real llama.cpp qwen4exp graph calls `sabah_rt.dll` at `MUL_MAT_ID`;
- host-backed original GGUF expert ranges are retained in a native Sabah LRU;
- the authoritative device `selected_experts` IDs are copied with their real
  GGML strides and used without substitution;
- the full graph completes one deterministic token and matches the reference
  token ID (`1596`, piece `We`).

Still not proven by the current integration run:

- independently dumped router IDs/weights against a reference run;
- full-model logits, intermediate states or MoE-boundary numerical equality;
- sequential 16/64-token equality;
- a Sabah-backed API server or a comparable benchmark.

The existing `GLM53_SABAH_TRACE` and `GLM53_MOE_TRACE` changes materialize or
record tensors such as `ffn_moe_topk`; they are useful diagnostics but cannot be
the production routing authority.

## Chosen implementation strategy

The implemented target is a reversible **Strategy A/C hybrid**:

1. Keep `qwen4exp`'s full llama.cpp graph unchanged when Sabah is disabled.
2. Add an optional native adapter at the scheduler/backend boundary where the
   exact `MUL_MAT_ID` IDs and host expert tensor are both available.
3. Give that adapter a persistent per-device residency table keyed by
   `(tensor identity, block, expert, role)` and an exact source-range callback.
4. The native adapter keeps the original IDs for routing/aggregate ordering,
   caches exact expert byte ranges keyed by `(source tensor, expert)`, and
   launches an exact quantized CUDA `MUL_MAT_ID` kernel against a device pointer
   table. It does not create a full-shaped device copy or remap expert IDs.
5. Keep reference and Sabah modes explicit. A requested Sabah benchmark must
   fail loudly when the native adapter is unavailable; it must never silently
   fall back to `--cpu-moe`.

This is intentionally a target architecture, not a claim that the current
checkout has completed it. The present scheduler copy path allocates/uses a
full-shaped backend tensor and copies only selected ranges into it. It has no
persistent LRU slot mapping and cannot be relabelled as Sabah execution.

## Concrete blocker for v1.0

The original standalone `sabah_moe_block` API remains, but the runtime now also
exposes a native tensor-backed `sabah_rt_mul_mat_id` ABI for the llama.cpp
boundary. It accepts GGML strides, downloads the authoritative IDs, fetches
the exact source expert ranges into the native LRU, and returns the routed
projection into the graph's device output tensor.

Bridging this requires a native adapter and either:

- a persistent full-index device representation (likely virtual/sparse
  addressing), or
- a new compact expert op that carries authoritative IDs plus a slot map while
  keeping the original IDs for router weights and aggregate ordering.

Gate F's first-token sub-gate is now PASS. Gate F as a release gate remains
open until the independent correctness ladder and sequential tests are added.

The release should pin the above llama.cpp commit (or a clean commit plus a
small documented patch set). The current `$DRIVE\llama-glm53` tree contains
experimental, unrelated local additions and is not a shippable dependency
snapshot. A future release artifact must record the exact clean base commit,
Sabah patch, CUDA build flags and native runtime DLL beside its results.
