You are a senior backend engineer helping a small team ship a GPU inference service.

User: We run a single RTX 5060 Ti (16 GB) on a Windows 11 box and serve a 48-layer MoE
model. The plan was to keep a hot subset of experts in VRAM and stream the rest from an
NVMe drive. In our first test the first token took 13 s and steady decode settled around
20 tokens/s, but the number moves between 2 and 20 tokens/s depending on the prompt. Is
that expected, or did we mis-configure something?

Assistant: Both. A cold tier has to fill, so 13 s to first token with 53 prompt tokens
looks like the fill plus the first routing decisions, not a bug. The 2-20 tokens/s range
is the interesting part: it means your steady state is not steady. Two prompts with the
same length can differ by 3x because they route to different experts, and the cost of a
token is dominated by how many expert tensors you have to fetch rather than by the compute
you do. Before touching the kernel, log three things per decode token: how many experts
you had to fetch, how many bytes those fetches read, and how long the fetch waited. If the
fetch wait is more than half the token, a faster kernel will not help.

User: We logged it. One prompt reads 175 MB per token, the other 132 MB, and both sit near
90% hit rate. The first one has 257 misses per token and the second 195. So the second one
reads less but is also 4x faster than the first. That does not line up with the byte counts.

Assistant: Then the bytes are not the whole story; the read latency is. Two working sets of
similar size can have very different access patterns: one touches a few large contiguous
expert blocks, the other touches many scattered ones. With a queue depth of eight and
direct I/O, scattered reads pay a per-request setup cost that contiguous reads amortize. It
is also worth checking whether the faster prompt is simply being served from the operating
system page cache because you ran it second. Run the pair in both orders on a freshly
rebooted machine, and log the per-token read time distribution, not just the mean. If the
distribution is bimodal, part of your traffic is cached and part is not.

User: We re-ran it in the opposite order and the fast prompt stayed fast, so it is not the
page cache. We also noticed that the clock drops to P3 with memory at 7001 MHz for about
seven seconds in the middle of a run, and the token time roughly doubles while that
happens. Could that be the whole mystery?

Assistant: Seven seconds of a 4x slowdown is enough to move a median, so it is part of it,
but it cannot explain a stable 4x difference across a whole run unless the two prompts put
the GPU in different power states. The test is to pin both the SM and the memory clock
floors before the run and repeat both prompts. If the gap survives pinning, the clock is
not the cause and you should treat the low state as a separate bug that only affects your
reported numbers, not the model's behaviour.

User: Pinning the SM floor alone did not stop the memory clock from dropping. Pinning both
did, and now every run is clean. With clocks pinned, the fast prompt is 47 ms per token and
the slow one is 176 ms, so the gap is real. What would you look at next?

Assistant: With the clock out of the way, look at what the slow prompt is actually waiting
on. Decompose the token into three budgets: the Sabah bridge plus expert kernels, the dense
part (attention, shared experts, the output projection), and the host submission gaps. The
slow prompt at 176 ms with 175 MB of fetch is almost certainly sitting in the fetch wait; at
1 GB/s effective, 175 MB alone is 175 ms, so the kernel is not your problem at all on that
prompt. The fast one at 47 ms and 132 MB cannot be reading from disk at that rate, so it must
be hitting your VRAM tier much more effectively per byte. Compare the miss *reasons*: are
you evicting because of capacity, or because the replacement policy is thrashing a small set
of experts that alternate on every layer?

User: We do not record a reason per eviction, only a count. Would adding that be worth the
effort before trying anything else?

Assistant: Yes, but keep it cheap: record the layer and the expert id with each eviction into
a fixed-size ring buffer and dump it at exit. You do not need per-eviction attribution in the
hot path. With that trace, one of two things will be obvious within a hundred tokens: either
a few thousand (layer, expert) pairs dominate the evictions and a better policy wins, or the
evictions are spread across the whole space and the tier is simply too small for the prompt.
Those lead to completely different fixes, and guessing between them has already cost you a
day.

User: One more thing before we instrument. Our token times at 128K context are identical to
128K at 512 context for the fast prompt, and identical byte counts. Does that make sense?

Assistant: It makes sense if your per-token routing depends only on the current token
distribution and the recent window, not on the whole context. Attention over a long context
changes the hidden state, so I would expect *some* drift in the routing, but if the model is
deterministic and the decoded token stream is identical in both runs, the expert selection
will be identical too and the byte counts must match exactly. That is a useful control: it
tells you the 128K cost you are seeing is the compute buffer and KV growth, not the expert
path. Check that the two runs decode the same token ids; if they do, you have proved the
expert traffic is context-independent for this prompt, and you can stop worrying that the
long context is polluting your tier measurements.

User: Assuming the trace shows a small set of hot experts being evicted repeatedly, what is
the cheapest change that does not alter routing or output?

Assistant: Reorder, do not replace. Keep the same set of resident experts and the same
fallback behaviour, but make the eviction policy aware of the next layer you are about to
run: when a layer is about to need expert E and E is resident, nothing happens; when you must
choose a victim, prefer one whose next use is furthest away, and never evict an entry that is
already on the critical path of the current token. That is a pure scheduling change, it does
not touch the math, and it is provable by byte-identical logits. The other cheap change is
prefetching the next layer's likely experts while the current layer computes, which converts
a stall into overlap with no change in what is served.

User: Good. We will instrument evictions with the layer and expert id, verify that the two
prompts decode identical ids at both contexts, and then try next-use-aware victim selection
behind a flag. Please write the plan as a short checklist we can follow, including what we
must record so that the result is provably safe.
